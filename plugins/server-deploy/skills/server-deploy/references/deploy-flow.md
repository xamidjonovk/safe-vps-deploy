# Git and release flow

1. Inspect git status, remote, branch and changed files. Run the project's meaningful checks. Prepare only project changes for a commit; never include `.env`, private keys or unrelated IDE files. Use existing authorization to push the deployment commit; ask only about an ambiguous target or unrequested external changes.
2. Project-scoped SSH: `ssh -i <key> -o UserKnownHostsFile=<known-hosts> -o StrictHostKeyChecking=yes -o BatchMode=yes -p <port> sdp-<project>@<host> sudo sdp preflight`. Verify health and resources. Use `port-suggest` before selecting the localhost application port.
3. `sudo sdp repo-init <url> --branch <branch>`, then `sync`. Private repositories require a read-only repository deploy key. Add it with the user's authorization to configure repository access; use an existing GitHub connector/CLI when sufficient. Never broaden to a personal account token on the server. Verify the intended SHA after sync.
4. `env-template`, `env-gen` for random secrets and `env-set` for config/reference values; finish with `env-status`. Never pipe the workstation `.env` to the server. Quote `${REFERENCES}` across both SSH shells. Set `compose_file`, health URLs and wait timeout using `sdp config`. Choose only required dependencies; do not add Redis/Celery/frontend when absent.
5. `validate`, then a database backup if schema changes are involved. Inspect available project-scoped backup capabilities before running one. No blind restore or destructive migration downgrade. `deploy --sha <SHA>` performs build/up/health/rollback. Give long builds bounded waits and concise progress updates.
6. Check `status`, `ps`, masked logs and expected HTTP endpoints. Compare the pre-deploy server inventory with the post-deploy inventory; harmless elapsed time is not a service state change. If readiness fails, preserve diagnostic evidence and use broker rollback. First deployments have no known-good release to roll back to.
7. Route a new domain only when DNS and ownership are known. Check nginx syntax before reload, touch only this project's domain file, and verify existing routes afterwards. Never take over 80/443 from a different reverse proxy. A localhost endpoint may instead be accessed with an SSH tunnel; do not expose it publicly without a requested routing plan.
8. CI is separate from a one-off release. Preserve working tests/build jobs, add deploy concurrency (`cancel-in-progress: false`) and a deploy timeout. Use [templates/github-workflows/deploy.yml](../templates/github-workflows/deploy.yml) for the restricted CI key. Pipe `ci-key` into the secret store without printing it. Set known hosts and the actual SSH port. Track the run to completion; only then report CI success.

Application rollback can still be incompatible with a new schema. Keep backward-compatible migrations or stop for a reviewed restore plan. Neither broker rollback nor this skill guarantees a database rollback.
